# 产品铁律（最高优先级，与任何其它文档冲突时以本文为准）

> 立此铁律的时间：2026-11-23，客户原话：
>
> **「我们不是定制化的开发页面，我们是要做一个模板库 + 数据孪生引擎 +
> 业务逻辑绑定 + AI 自动化构建 + ThingsBoard 的接口的整个闭环。」**

---

## 一、我们做的是什么（以及不是什么）

**不是**：给某个客户、某个园区、某个冷热站**手写一页大屏**。

**是**：五个可复用的层次，每一层都要能被下一个客户/场景**重新组合**。

```
┌─────────────────────────────────────────────────────────────┐
│ ⑤ AI 自动化构建                                              │
│    输入：模板包 + 设备映射 + 数据绑定要求 + 新建场景表单       │
│    输出：能出数的大屏（不是空骨架）                            │
├─────────────────────────────────────────────────────────────┤
│ ④ 业务逻辑绑定                                              │
│    遥测/属性/告警/命令 如何挂到 3D 对象与部件上               │
├─────────────────────────────────────────────────────────────┤
│ ③ 数据孪生引擎                                              │
│    PlayCanvas 渲染 + 动画 + 状态驱动 + 风格套装规则            │
├─────────────────────────────────────────────────────────────┤
│ ② 模板库                                                    │
│    template.json + binding-plan + scene-form + gaps          │
│    可导出、可校验、可版本化                                   │
├─────────────────────────────────────────────────────────────┤
│ ① ThingsBoard 接口                                          │
│    设备/遥测/属性/告警/RPC/拓扑/统计 —— 统一从平台取          │
└─────────────────────────────────────────────────────────────┘
```

---

## 二、判据：每一行代码都要能通过这三问

写任何一行代码前，先问：

### 问 1：这是**机制**还是**某个场景的数据**？

| 机制（写进代码/模板） | 场景数据（写进平台/配置/库） |
| --- | --- |
| 「部件按 `dataSource` 决定读遥测还是统计」 | 「天骄的 `system-power` 卡读场站用电量」 |
| 「风格套装可携带 `pipe.flowSpeed`」 | 「`hvac-hud-v1` 的流速是 0.8」 |
| 「订阅范围由 topology scope 解析」 | 「天骄的 scope 是 `dfbc1da0…`」 |
| 「趋势卡支持时/日/月/年」 | 「这块卡默认选『日』」 |

**违反的信号**：代码里出现具体设备 id、场站 id、客户名、机型名。

### 问 2：下一个客户（不同设备、不同 GLB、不同布局）能用吗？

如果答案是「要改代码」，那这件事就没做完 —— 要么改成配置驱动，
要么补进模板包的 schema。

**反例（真实踩过）**：

- 把「9 台之和」写死成 `aggregate` 槽位 → 换个客户是 5 台就不对
  → 正解：`aggregate` + `filterText` 由布局配置给
- 把碳排系数写死在渲染里 → 正解：系数来自平台 `byKind[].kgco2`
- 把 `kWh` 和 `tce` 混用 → 正解：接口分别给 `byKind.elec` 与 `series.tce`

### 问 3：AI 只读模板包和表单，能不能建出同样的东西？

如果某个能力只存在于"某次对话里我手动改的"，那它就**丢失了**。
必须落成：模板字段、部件类型、配置项、或 skill 里的可执行步骤。

## 二之二、★ 命名铁律：技术名归平台，显示名归客户（2026-11-23 立）

客户原话：

> **「由于 TB 的内部机制，资产、设备都不能重名，所有你看平台的设备的技术名
> 都很长、但是对用户不友好，你要用 label 来给客户看，包括标准 key 也要用中文。」**

### 为什么技术名必然很长

ThingsBoard 里 `name` 是**唯一键**，同一租户下不能重名。
为了唯一，名字里被塞进了型号、场站后缀：

| 实体 | `name`（技术名，唯一） | `label`（显示名，给人看） |
| --- | --- | --- |
| 设备 | `PowerMeter-3P-CHINT·平台演示中心` | `正泰三相电表 DTSD3366D` |
| 设备 | `天骄-PLC控制柜-1·生产园区` | `PLC控制柜 1` |
| 资产 | `天骄冷热站·生产园区` | `天骄冷热站` |

用户看到 `PowerMeter-3P-CHINT·平台演示中心` 只会觉得这是个数据库 ID。
**`name` 是给平台用的，`label` 是给人看的。**

### 硬规则

| 层 | 规则 |
| --- | --- |
| **显示层（UI/大屏/告警/报表）** | **一律用 `label`**；`label` 为空时才回落到 `name` |
| **标识层（绑定/接口/存储/日志）** | **一律用 `name` 或 `id`** —— 用 label 会因为重名或改名而断链 |
| **遥测/属性 key** | 显示时必须有**中文名**；技术 key（`temperature`）只出现在配置和契约里 |

### ★ 必须有一个统一函数，不能各处各写

**踩过的坑**：前端散落着 `device.label || device.name` 写法，
每处都靠人记得写 `|| name`。漏一处就露出技术名 ——
而这类缺陷**不会报错**，只能靠人盯着屏幕发现。

**正解**：`displayNameOf()` 单一入口，所有显示层调用它。
新增显示位置时，编译器/评审只需检查「有没有走这个函数」。

### ★ 中文 key 名从哪来（三种来源，优先级从高到低）

1. **场景实例层**（`scene-widgets` 的 `slots[].label`）——
   同一个 `temperature` 在冷热站叫「出水温度」、在机房叫「回风温度」，
   必须允许**按场景改名**
2. **数据字典层**（场景 `dataSources` 里登记的 key → 中文名）——
   开发人员在在线编程时能查到「这个设备有哪些遥测、中文叫什么」
3. **兜底**：直接显示技术 key，并**明确标出它是技术名**
   （比如 `temperature`），不要伪装成中文

**绝对禁止**：把中文名写成一堆 `if (key === 'temperature') return '温度'`
的硬编码分支 —— 换个客户、换套设备就全错。

### 判据（自查）

- 大屏上**不应出现**：`·平台演示中心`、`PowerMeter-3P-`、`天骄-` 这类技术名片段
- 大屏上**不应出现**：`temperature` / `power` / `running` 这类裸 key
- 设备下拉框、告警列表、设备专题卡都要过同一条判据

## 二之三、★ 资产分组驱动的场景跳转（2026-11-23 客户提出）

客户原话：

> **「你看客户的设备分组里面都是用资产来区分的，现在 3d-ngx 场景也是关联分组
> （分项/分区等），咱们的数据孪生要支持不同资产绑定的场景的跳转。」**

### 平台侧的真实结构（已实测）

设备不是平铺的，而是挂在**三层资产**下：

```
用能分项·平台演示中心        (asset type: energy_item_library)   ← 库
  └─ 用能分项·…·三相园区      (asset type: 场站分组)              ← 场站实例
       └─ 动力分项 / 照明分项 …                                   ← 具体分组
            └─ 设备（Contains 关系）
```

同构的还有三个库：`energy_space_library`（空间位置/分区）、
`energy_area_library`（用能区域）、`energy_usage_library`（能耗类型）。

### 需求

场景已经能绑「分组」（`ScenePlatformRef.roots` 是资产 id 列表）。
现在要求：**在这些资产绑定的场景之间跳转**。

即：站在「动力分项」的场景里，能看到并跳到「照明分项」的场景。

### 为什么这不是「子场景」那么简单

现有的 `scene-navigation.ts` 是按 **topologyId** 组织面包屑（上级/下级）。
而资产分组是**平级**关系 —— 动力分项与照明分项之间没有上下级，
它们都挂在同一个「场站分组」资产下。

所以需要**两种导航语义并存**：

| 导航类型 | 依据 | 用在哪 |
| --- | --- | --- |
| 层级式（已有） | `topologyId` 父子 | 场站 → 机组 → 部件 |
| **平级式（待实现）** | 同一资产分组下的兄弟场景 | 分项 A ↔ 分项 B |

平级跳转必须**记来源**，否则用户跳到第四个分项后找不到回「动力分项」的路。
建议用一个「分组上下文」：进入时记住是哪个资产库（`energy_item_library`），
所有兄弟场景都在这个上下文里列出来。

### 实现要点（未做，先记录）

1. **按资产反查场景**：需要一个「资产 id → 场景列表」的查询。
   平台目前只有按场景查 `roots`，没有反向索引 —— 要么后端加接口，
   要么前端一次性拉全部场景在本地建索引（场景数量少时可行）。
2. **场景必须声明自己是哪个分组**：`roots` 已有，但缺少「分组库类型」
   （分项 / 分区 / 区域）。补一个 `platform.groupKind` 字段。
3. **跳转入口放在哪**：不能只放面包屑（那是层级式的语义）。
   建议在顶栏加一个「同组场景」下拉，或在场景里显示兄弟分项标签。
4. **无场景的分组要显式标注**：某个分项还没有建场景时，
   下拉里应该显示「未建场景」而不是消失 —— 否则用户以为分组丢了。

## 二之四、★ 诊断依据铁律：每个指标必须能追溯到官方文档（2026-11-23 客户立）

客户原话：

> 「采集的指标参数中有备注、异常检测的说明指导……现在用户他们在排查问题的
> 时候，就是参考这个手册的说明找原因的。后面的数据孪生、平台异常告警等
> 分析都是要依靠这些官方说明文档的。」

### 问题

一个遥测点只说「叫什么、单位是什么、怎么换算」是不够的。现场真正要回答的是：
**「这个数不对，是哪儿坏了？该查什么？」** 现在这个答案在 PDF 里、在老师傅脑子里。

### 硬规则

1. **每个标准 key 必须有 `diagnosis`**：正常范围（含工况）+ 异常含义 +
   对应故障码 + 排查动作 + 文档条款号。字段结构见
   `docs/twin-unit-maindata-plan.md` §4.6。
2. **`normalRange` 必须带 `when`**（工况）。同一个温度在制冷/制热两套范围，
   缺工况必误判。
3. **`docRef` 必须能回溯到章节/页码**，否则文档改版时无法更新，也无法核对。
4. **没有官方依据就留空，不许编造**。编造的阈值会直接变成误报，
   比没有依据更糟。
5. **故障码单独建字典**，key 只存引用 —— 否则同一份分析文字会抄几十遍，
   改一处忘一片。

### 为什么这是铁律而不是「补充说明」

因为它有**四个消费方**，每个都不能自己编口径：

| 消费方 | 靠它做什么 |
| --- | --- |
| 现场排查 | 告警面板直接给「故障分析 + 解决方案」 |
| 数据孪生 | 判定 3D 场景里设备该绿、该黄还是该红 |
| 平台异常告警 | 告警阈值只能从这里来，不能凭感觉拍 |
| AI 自动化构建 | 建场景时自动带出诊断文案，不编造 |

一个客户填了、另一个没填，引擎就得两套逻辑 —— 所以它是**接口契约**，
不是可选的注释。

## 三、五层各自的"完成"标准

### ① ThingsBoard 接口层

- **不重造**：能复用平台接口就复用（`/api/energy/comprehensive`、
  `/api/energy/tou-analysis`、`/api/plugins/telemetry/...`）
- **不越权**：一律走 provider 的 `requestJson`，不自己拼 token
- **接口缺口要补在平台**，不要在前端造一套平行实现
  （已例：`series` 缺分品种用量 → 改 `ComprehensiveEnergyService` 加 `byKind`）

### ② 模板库层

- 模板只描述**结构与绑定意图**，不描述具体设备
- `gaps.json` 必须明确「模板管不到、必须实例层补」的部分
- 模板必须能被 `scripts/export-template-package.mjs` 导出并校验

### ③ 数据孪生引擎层

- 渲染行为由**规则**驱动，不由代码分支硬编码
  （已例：管道流速/阀门颜色/状态环 → 风格套装 `render` 规则）
- 缺规则时走**默认值**，不是不渲染
- 动画/透明度这类视觉参数一律可从外部覆盖

### ④ 业务逻辑绑定层

- 绑定关系存在平台（`scene-widgets` / `bindings`），不在浏览器
- 「设计时看到的 = 运行时看到的」是硬要求（所见即所得）
- 聚合口径必须可配（`aggregate` + `filterText`），不能写死台数

### ⑤ AI 自动化构建层

- 输入契约写进 skill：`docs/3d-rendering-and-assets.md` §三
- 每个能力都要有**可执行的验收判据**（命令或浏览器断言）
- 静默失败清单持续维护 —— 不报错但看着不对的，必须列进去

## 三之二、风格套装规则落地的四个坑（2026-11-23 实测）

「让套装驱动渲染」听起来只是「读个配置、设个值」，实际连踩四层。
记下来，因为每一层的失败方式都是**静默**的。

### 坑 1：类型里没有字段，解析就永远拿不到

`TopologyGraph` 接口**没有** `packId/packVersion/stylePack` 三个字段。
平台拓扑接口明明返回了 `hvac-hud-v1@1.0.0`，但走 graph 路径打开的场景
永远拿到 `undefined`。

- 判据：`document.platform.stylePack === null` 而平台接口有值
- 修法：补类型 + 补解析（`first(row,[...]) || first(graph,[...])`）

### 坑 2：本地缓存优先，把平台权威配置盖住了

场景文档优先从 IndexedDB 读。旧缓存里的 `platform.topologyId`
和 `platform.stylePack` 都是 null —— 早期版本没写这些字段。

- 连锁后果：`topologyId` 为 null → 同组导航、套装规则全部失效
- 修法：**URL 的 `:sceneId` 才是权威**；套装规则再从平台回查一次

### 坑 3：`cancelled` 布尔把最后一次结果丢掉了

场景加载会多次更新 document（骨架→模型→布局），effect 反复重跑。
前一次的 `cancelled=true` 丢弃结果，最后一次的异步链还在路上 ——
用户切走时规则就永远没应用。

- 判据：trace 显示 `resolveRules:done found=[pipe,valve,device]`，
  但引擎 `getRenderRules()` 仍是默认值
- 修法：用序号（seq）代替布尔，只丢弃**更旧的**结果

### 坑 4：`assignAnimation` 的 speed 参数对已存在的 state 无效

```js
// 传了 0.8，读回仍是 1
anim.assignAnimation(clip, track, undefined, 0.8);
```

组件方法只在**首次建 stateGraph** 时把 speed 写进 state；后续走
`layer.assignAnimation(path, track, speed, loop)`，那一层不更新已有 state。

- 修法：挂载后**显式** `state.speed = flowSpeed`，不依赖 API 隐式行为
- 这也是唯一确定生效的路径（热更新，画面不跳帧）

### 验证方式（可复用）

```bash
# 期望：L-101-1_flow 的 speed = 0.8（来自 hvac-hud-v1 的 pipe.flowSpeed）
# 在浏览器 console 里：
#   window.__attachSpeed   # 临时诊断钩子，验证完已移除
# 或直接读 layer：
#   pipe.anim.findLayer('Base')._controller._states[...].speed
```

## 四、这条铁律如何影响日常判断

| 场景 | 错误反应 | 正确反应 |
| --- | --- | --- |
| 客户说「这块卡改成显示耗电量」 | 直接改这块卡的代码 | 加「统计口径」配置项，改数据 |
| 客户说「这个园区有 12 台机组」 | 把 12 写进代码 | 由 scope + filterText 决定 |
| 客户说「管道要流动」 | 针对这个 GLB 写死动画名 | 按已知后缀规则解析，通用 |
| 发现平台接口缺字段 | 前端拼凑出近似值 | 补平台接口（加法，不破坏契约） |
| 修一个只影响某场景的 bug | 加 `if (topologyId === 'xxx')` | 找通用判据；确实无法通用时，记为已知限制并写进文档 |

## 五、违反铁律的已知事故（引以为戒）

| 事故 | 本质 |
| --- | --- |
| 部件布局里写死「9 台机组」 | 换个客户台数不对 |
| 趋势卡拿 `tce` 当耗电量展示 | 单位混淆，客户按电价一乘就露馅 |
| 风格套装只有 label 没有 `render` | 描述是空话，选了等于没选 |
| 演示数据开关只删按钮不删下游分支 | 残留状态让指令不发后端 |
| `parseSceneWidget` 白名单漏字段 | 配置存住了但读不出来 |
| 大屏显示 `PowerMeter-3P-CHINT·平台演示中心` | 把平台唯一键当成给人看的名字 |
| 遥测键直接显示 `temperature` | 技术契约泄漏到界面 |

这些都不是「写得不够好」，而是**把机制做成了定制**。

## 七、给 AI 的硬性要求

1. **改任何东西前**，先判断它属于哪一层。
2. **新增能力**必须同时更新：代码 + 模板 schema（如适用）+ skill + 验收判据。
3. **不允许**为了"这次能跑"而引入只对当前场景成立的逻辑。
4. **发现平台缺口**，补平台，不要在前端糊一个平行实现。
5. 写文档时**写清楚"为什么"，不只写"是什么"** —— 下一个 AI 靠这个做判断。
